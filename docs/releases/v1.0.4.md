# mix2api v1.0.4

v1.0.3 之后的补丁版：CodeArts 模型目录按上游真实能力宣告视觉支持。

## 这个版本做了什么

- **`/v1/models` 宣告视觉能力**：CodeArts 模型条目现在读取上游 `supports_images`，并输出与 WorkBuddy 相同的能力字段：`capabilities.vision`、`supports_vision`、`supports_images`、`vision`、`multimodal`、`abilities.vision`、`input_modalities`、`modalities`、`architecture`。
- **只对真正支持读图的模型宣告**：当前 `Qwen3-VL-235B`、`kimi-k2.6-vl` 为 true；`GLM-5.2`、`kimi-k3`、`deepseek-v4.1-flash` 等上游明确返回 `The request model is not multimodal`，因此为 false，不再向客户端误报。
- **DSH / 客户端可直接启用图片输入**：DSH 只读模型条目的 `input` 模态；现在视觉模型会带 `input_modalities: ["text", "image"]`，粘贴图片不会再被本地判成纯文本模型。
- **图片透传继续保留**：OpenAI `image_url`、Responses `input_image`、Anthropic `image` 块统一归一化为 `image_url`；文本-only 消息仍保持原纯字符串格式。
- **回退规则**：上游 builtin 目录没有 `supports_images` 时，只用已知的 CodeArts VL 型号兜底；不拿 WorkBuddy 的声明覆盖 CodeArts 的实际能力。WorkBuddy 把 GLM-5.2、kimi-k3、deepseek-v4.1-flash 标成可读图，但 CodeArts 实测会返回 `The request model is not multimodal`，所以这些模型在 CodeArts 侧保持 false。

## 升级

- 直接替换镜像或代码即可，无数据迁移；默认端口仍是 `58675`。
- 如果客户端此前缓存了 `/v1/models`，刷新一次模型列表即可看到新的视觉标记。
- 图片能力取决于模型；文本模型收到图片时上游会返回 `not multimodal`。

## 验证

- 243 个测试套件全过。
- 真实 `/v1/models?realm=codearts` 输出：`Qwen3-VL-235B`、`kimi-k2.6-vl` 为 `capabilities.vision: true`，`input_modalities: ["text","image"]`；`GLM-5.2`、`kimi-k3`、`deepseek-v4.1-flash` 为 false。
- 真实图片请求仍正常：发送写着 `47` 的图片，返回 `/* 47 */`。
- 对 GLM-5.2 / kimi-k3 / deepseek-v4.1-flash 发图片，上游明确返回 `The request model is not multimodal`，与目录标记一致。

## Docker 镜像

已发布到 GitHub Container Registry，支持 `linux/amd64` 与 `linux/arm64`：

```bash
docker pull ghcr.io/ayeaaaa/mix2api:v1.0.4
docker pull ghcr.io/ayeaaaa/mix2api:latest
```

直接运行：

```bash
docker run -d --name mix2api -p 58675:58675 \
  -v "$PWD/data/accounts:/app/accounts" \
  -v "$PWD/data/usage:/app/usage" \
  ghcr.io/ayeaaaa/mix2api:v1.0.4
```

或用本包里的 `deploy/docker-compose.image.yml`：

```bash
cd deploy
docker compose -f docker-compose.image.yml up -d
```

## English summary

`mix2api` v1.0.4 makes CodeArts `/v1/models` advertise vision support from the upstream `supports_images` flag, using the same capability fields WorkBuddy emits. Only `Qwen3-VL-235B` and `kimi-k2.6-vl` are marked image-capable today; `GLM-5.2`, `kimi-k3`, `deepseek-v4.1-flash` and others are marked text-only because the upstream answers “not multimodal”. Image passthrough for OpenAI, Responses and Anthropic content blocks is retained. The multi-arch image is published as `ghcr.io/ayeaaaa/mix2api:v1.0.4` and `:latest`.
